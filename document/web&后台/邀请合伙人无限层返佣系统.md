# 邀请合伙人无限层返佣系统

# 业务定义

## 1\.1 核心业务模型

**模型定义：无限级差佣金制**

- 平台为每个一级合伙人设定一个返佣比例上限（运营可在权限后台配置，当前原型演示为 **80%**），该比例即为此合伙人整条业务线的「总佣金包」上限参考。

- 合伙人可以无限层级地发展下级合伙人（平台对**新增发展**设有最多 **10 层**合伙人层级限制，见 §1.4），每一级合伙人的返佣比例由其直属上级设定，且**不得超过**上级自身的比例。

- **级差与合规**：上下级比例**允许相等**（级差 = 0，该上级在该笔交易上级差为 0，属正常配置）。下级返佣比例**不得超过**上级返佣比例。

- 当终端用户（直客或合伙人自营）产生交易手续费时，系统沿邀请链路向上逐级计算级差佣金，直到一级合伙人为止。

**角色定义**

|角色|账号类型|交易时身份|是否参与返佣分配|
|---|---|---|---|
|一级合伙人|Agent|渠道/交易者|是，享受自返佣，并从下级合伙人的级差中获利|
|N级合伙人 \(N≥2\)|Agent|渠道/交易者|是，享受自返佣，并从直属下级合伙人的级差中获利|
|直客|Client|纯交易者|是，为上级合伙人贡献级差的「燃料」，自己不拿返佣|

**核心原则：合伙人自营也参与返佣**

- 合伙人用自己的合伙人账号交易，自己拿走自己返佣比例对应的佣金（自返佣）。

- 同时，他的所有上级依然按级差规则分钱。

## 1\.2 返佣计算规则

### 规则一：自返佣

- 触发条件：代理使用自己的代理账号进行交易并产生手续费。

- 计算：`该代理的返佣比例 × 该笔手续费`

- 拿到钱的人：该代理本人。

### 规则二：直客级差

- 触发条件：直客进行交易并产生手续费。

- 计算：

    - 直客的直属上级代理：拿走自己**全额**返佣比例对应的佣金。

    - 该上级的每一位上级：拿走 `(自己的返佣比例 - 直属下级代理的返佣比例)` 的级差部分。

- 如果上级与直属下级的比例相同，则该上级在这笔直客交易上级差为 0。

### 规则三：代理自营级差

- 触发条件：某代理用自己代理号交易产生手续费。

- 该代理自己先拿走自返佣（规则一）。

- 他的所有上级，按规则二的方式，从他身上计算级差，即 `(上级比例 - 该代理比例) × 该笔手续费`。

### **公式总结：**

- 对任意一笔交易：

    1. 确定交易发起人 `X`（可能是代理或直客）。

    2. 如果 `X` 是代理，`X` 获得 `比例_X × 手续费`。

    3. 沿着 `X` 的上级链路向上遍历，当前上级 `P`：

        - 如果 `P` 是 `X` 的直属上级，`P` 获得 `(比例_P - 比例_X) × 手续费`

        - 否则，`P` 获得 `(比例_P - 比例_直属下级) × 手续费`

    4. 直到一级代理停止。

## 1\.3 返佣结算流程

**整体流程：日结制**

1. **交易数据采集**：系统实时记录每一笔交易的手续费。

2. **每日结算触发**：每日 00:00 \(UTC\+8\)，系统对前一日 00:00:00 至 23:59:59 的所有交易进行结算。

3. **数据同步**：生成用于审查的对账 CSV 包（表 1–4，及建议一并导出的一级比例快照表 2a），进入风控审批队列。

4. **人工审查**：风控或运营人员登录后台「佣金对账与发放」页面，进行四步审计：

    - **总量对账**：用 Platform\_Summary 核对平台总手续费与总返佣预算。

    - **聚合校验**：用 Rebate\_Split\_Detail 的流水表通过 Excel 枢纽分析，反向汇总每个代理应得总金额。

    - **差异比对**：将汇总结果与 System\_Proposed\_Payout 做 VLOOKUP 比对，排查是否存在非零差异。

    - **穿透抽样**：随机抽检一个代理，验证其分账流水是否与 Affiliate\_Map 中的比例关系吻合。

5. **审批执行**：

    - **通过**：风控点击「审核通过并放款」，系统将最终实发金额执行发放。

    - **拒绝**：风控填写拒绝原因，该批次标记为「已拒绝」，打回重算。

6. **数据归档**：所有 CSV 文件和审批记录存档备查。

## 1\.4 返佣比例调整、关系迁移与运营权限

### 运营权限上限与审批

- 每位市场运营在权限配置中设有 **一级合伙人返佣比例上限（%）**（原型演示为 **80%**），页面顶栏展示「权限上限: XX%」。

- **≤ 运营上限** 的比例调整：在返佣树内提交后**即刻生效**（无需审批）。

- **&gt; 运营上限** 的一级绑定或比例调整：须提交审批，流程为 **市场运营提交 → 风控审核 → 老板审批**（风控通过后同步 Lark，老板可在 Lark 或后台通过）；**审批通过后即刻生效**。

- **≤ 运营上限** 的一级合伙人绑定：提交后**即刻生效**（无需审批）。

- **同一批提交中若混合「权限内」与「超上限」修改**：仅超上限项进入审批；权限内修改**自动放弃**（输入框回滚），须先处理超上限申请。

### 两类返佣关系变更动作

后台涉及**返佣归属关系**变更的配置动作有两类：

| 动作 | 入口 | 典型场景 |
|---|---|---|
| **迁移返佣关系** | 侧栏 · 迁移返佣关系 | 将已有用户/代理挂到新的上级之下（仍在平台返佣体系内） |
| **新增一级合伙人** | 合伙人列表 · + 新增一级合伙人 | 将普通用户/直客/N 级代理**升级为一级代理**（新建 L1 伞） |

**用户类型口径**（下文组合表均使用此三分法）：

| 类型 | 定义 |
|---|---|
| **普通用户 / 合伙人直客** | 非合伙人账号；含平台普通用户、某合伙人邀请的直客 |
| **N 级代理** | 合伙人账号且**不是**一级代理（系统 L2–L10） |
| **一级代理** | 合伙人账号且为 L1 根节点 |

### 原上级 · 数据边界（两类动作统一）

无论**迁移**还是**升级为一级合伙人**，对**原上级**（迁移/升级前的直属上级或原归属链）统一适用：

| 维度 | 规则 |
|---|---|
| 返佣人数 | **不变**（历史归属人数不回溯扣减） |
| 交易额 / 返佣 | 变更生效后，该主体及其随迁移/升级带走的伞**不再为原上级产生新的**交易额与返佣贡献 |
| 历史数据 | 变更前已归属的数据**保留** |
| 生效时机 | 无需审批的配置**即刻生效**；须审批的**审批通过后即刻生效** |

**新上级 / 新 L1 伞**侧：迁移后业绩与返佣从生效时刻起按新关系重新累计（周期统计不继承原上级下的数字），详见「迁移后的返佣计算与业绩统计」。

### 返佣关系迁移

**可迁移主体**：一级代理、普通用户/合伙人直客、N 级代理均可发起迁移。

**可作迁移目标**：一级代理、N 级代理、**普通用户（非代理）**均可作为接收方。

**主体 × 目标 · 配置与范围**（核心组合表）：

| 迁移主体 ↓ \ 目标 → | 一级 / N 级代理 | 普通用户（非代理） |
|---|---|---|
| **普通用户 / 合伙人直客** | 须选择迁移后身份：**下级直客**（无需比例）或 **下级代理**（须配置比例 ≤ 上级）；直客随主体一并迁移 | **固定**为下级直客；**不可**选代理身份；**不可**配置返佣比例 |
| **N 级代理** | **整伞迁移**（全部下级代理 + 直客）；须配置迁移主体返佣比例 | **不支持**（代理不可挂到普通用户下级） |
| **一级代理** | **整伞迁移**（L1 伞下全部节点 + 直客）；须配置迁移主体在新上级下的比例 | **不支持** |

**说明**：

- 迁移到**合伙人**下级时，比例须满足：迁移比例 ≤ 目标上级比例。

- 迁移到**普通用户**下级时，仅变更邀请/归属关系，不涉及合伙人返佣比例配置。

- 迁移申请提交后进入 **风控审核**（无需老板审批）；**审批通过后即刻生效**。

- **迁移后的数据统计与返佣归属**见下文「迁移后的返佣计算与业绩统计」及「原上级 · 数据边界」。

#### 新增一级合伙人 · 主体差异

**可升级主体**：普通用户/合伙人直客、N 级代理（**已是一级代理**的不可重复设置）。

| 当前身份 | 升级后范围 | 配置项 |
|---|---|---|
| **普通用户 / 合伙人直客** | 主体本人 + 其**直客**一并挂到新 L1 伞 | 仅配置**一级合伙人返佣比例**；弹窗仅展示**自邀直客人数**（不列明细） |
| **N 级代理** | 主体 + **整伞返佣树**（全部下级代理与直客）挂到新 L1 伞 | 仅配置**一级合伙人返佣比例**；须 **≥ 直属下级合伙人最大返佣**（树内下级比例保留，后续可在返佣树调整） |

升级后对**原上级**的数据边界与「原上级 · 数据边界」一致。返佣比例 **≤ 运营上限** 即刻生效；超上限走一级绑定审批。

### 合伙人层级上限（10 层）与迁移

- 平台对合伙人账号设置**最多 10 层**合伙人层级（L1 为一级合伙人，向下至多 10 层合伙人节点）。

- **用户端（合伙人中心）**：合伙人**新增下级合伙人**时，若会导致链路深度超过 10 层，系统**禁止绑定**新下级。该限制约束的是**新增发展**，不自动裁切已存在的深层节点。

- **迁移返佣关系**：迁移可能使某条业务链在系统内的**实际深度超过 10 层**（例如将较深整伞挂到较浅的上级之下）。迁移完成后：

    - **已存在的深层合伙人节点及其关系保留**，返佣与结算按新关系继续计算；

    - **不因迁移而作废 10 层限制**——限制仍作用于**迁移之后的新增下级**；处于第 10 层及更深处的合伙人，在合伙人中心**不可再发展新的下级合伙人**（与「用户层不允许延续新的下级」一致）。

    - 直客绑定、交易、返佣计算不受「10 层」约束（直客不计入合伙人层数）。

### 迁移后的返佣计算与业绩统计

迁移风控审核通过并生效后，返佣计算**立即**按**新的上级关系**与**新的返佣比例**执行。

**统一规则**：

| 维度 | 规则 |
|---|---|
| 原上级 | 迁移生效后，该伞**不再累计**新的交易额、手续费、返佣贡献；历史已归属数据保留 |
| 新上级 | 迁移生效后，该伞的业绩与返佣贡献从 **0 重新累计**（周期统计不继承原上级下的数字） |
| 返佣计算 | 生效后按新关系与新比例统计、分账 |

**说明**：普通用户迁移仅变更邀请关系；代理用户为**整伞迁移**，伞内全部合伙人节点与直客一并变更上级。

## 1\.5 其他补充

### **活跃用户 / 活跃代理定义**

- 定义为「所选时间周期内，交易额 &gt; 0 的用户或代理」。

- 此指标为**查询时实时计算**，不需要数据落库，不需要维护每日活跃状态表。

- 举例：选择统计周期为「1W」，则统计近 7 天内有过至少一笔交易（交易额 &gt; 0）的用户/代理数量。

- **用户合伙人中心「用户规模」展示口径**：主行展示**交易用户**数（周期内交易额 &gt; 0）；次行灰色小字展示**总用户**数（注册或归属伞内总人数，含未交易者）。**交易用户**数据每天 **UTC+8 0 点**更新；列表表头「用户规模」带虚线下划线，鼠标悬停提示上述更新规则。

### **用户侧佣金与状态展示规则（合伙人中心）**

以下规则仅描述**合伙人登录后**在「佣金结算与发放」及「合伙人管理」中的展示逻辑，与后台批次状态、风控操作对应关系如下：

| 后台 / 系统事实 | 用户侧展示 |
|---|---|
| 当日批次**等待对账**，佣金尚未放款 | **待结算** |
| 当日批次**已审核通过并放款** | **已结算** |
| 当日批次**已拒绝**（打回重算） | 仍展示 **待结算**（不向用户暴露「已拒绝」） |
| 后台在批次**待结算**阶段对该合伙人**调减实发**（佣金对账与发放 · 批次明细【修改实发】） | 流水状态 **待结算**；返佣主行展示**调减后实发**；次行红色小字 **违规 −$XX** 展示扣减额（**违规扣减 = 原始佣金 − 实发**，即后台调减差额） |
| 上述批次**已审核通过并放款** | 状态变为 **已结算**；返佣金额与违规扣减展示口径不变 |
| 用户处于**任意冻结状态**（部分冻结 / 账户冻结等） | 当日返佣**暂停日结发放**；手续费仍正常计算；返佣数据照常统计并累计为**待结算**；解冻后**次日 0 点（UTC+8）**统一结算发放 |

### **用户冻结与返佣结算**

当用户账号处于**任意冻结状态**（含部分冻结、账户冻结等，见《[用户风控冻结](用户风控冻结.md)》）时：

| 维度 | 规则 |
|---|---|
| 手续费 | **正常计算**，不因冻结而停止 |
| 返佣统计 | **正常统计**（含直客返佣 + 合伙人级差返佣） |
| 日结算发放 | **暂停发放**，不计入当日应发放批次 |
| 待结算累计 | 冻结期间产生的返佣统一计入**待结算**金额 |
| 解冻后 | **次日 0 点（UTC+8）**对累计待结算金额统一结算发放 |

**普通用户 / 合伙人直客**与**合伙人**均适用上述规则。

**后台合伙人管理列表**展示每位合伙人的**待结算金额**；**结算状态**在冻结期间展示 **冻结待结算**；**冻结状态**列仅在存在冻结时统一展示 **部分冻结** 标签（不论具体冻结项类型），无冻结显示 `—`。

**用户侧**「佣金结算与发放」流水在冻结期间对应日期仍展示**待结算**状态，解冻后统一发放时状态变为**已结算**（见 §3.4）。

### **净收入（后台指标）**

- 对任意查询根节点（某一级或下级合伙人）：`净收入 = 该伞下净手续费 − 由该伞下交易触发的全部返佣支出`。

- 「全部返佣」包含分给伞内所有合伙人，以及分给伞外上级合伙人的级差（因这些级差均由伞下交易手续费产生）。

- 一级合伙人视角即整条业务线平台留存；下级合伙人视角为「以该合伙人为根的子树」对平台整体的净贡献。

# 后台管理：合伙人管理及结算对账

本后台面向两类内部人员：

- **运营/BD 同学**：负责配置和管理一级合伙人、调整返佣树比例、发起关系迁移（仅可见自己负责的数据）。

- **超级管理员 / 风控**：负责维护后台人员与页面权限（含一级合伙人返佣比例上限，见《[后台权限与角色管理](后台权限与角色管理.md)》），执行合伙人相关审批，以及每日佣金对账与发放。

## 通用交互约定

### 统计周期

列表页、详情页与团队穿透页均提供统计周期切换：**1D / 1W / 1M / 3M / ALL**（默认 ALL）。切换后，团队总交易额、返佣、净入金、用户规模等周期敏感指标同步刷新。列表与详情打开时默认继承列表当前周期。

**说明**：合伙人**列表**仍展示手续费、净收入等运营对账向列；**详情 / 团队穿透**页与用户 Web「合伙人管理」对齐，指标区为四卡（不含手续费、净收入独立卡），见 §2.1.4。

### 分页

合伙人列表、详情子表、返佣树一级支路、迁移预览树、结算批次与明细、操作记录、审批列表等长列表统一 **每页 10 条**，提供页码切换（含省略号大页数样式）。

### 地址与 UID 复制

UID、钱包地址、邮箱在列表、详情、树节点、结算、审批详情等处以缩写展示；**UID 为主键**。列表与子表将 **UID** 与 **钱包 / 邮箱** 拆为独立列（层级 **Lx · N 直属** 合并展示在「合伙人」列，不再单独占列）。各标识均支持一键复制完整值，复制成功有短暂提示。

### 页面路由（Hash）

支持浏览器 Hash 直达：`#agent`（合伙人列表）、`#partner-detail`（合伙人详情）、`#partner-detail-drill`（团队穿透）、`#rebate-tree`（返佣关系树）、`#migrate`（迁移返佣关系）、`#approval`（合伙人审核）、`#approval-migrate`（合伙人审核 · 深链至迁移类审批）、`#settlement`（佣金对账）、`#logs`（操作记录）。侧栏点击与页内跳转同步更新 Hash；进入返佣树时保留 `#rebate-tree`；团队穿透页保留 `#partner-detail-drill`。

| 字段 | 规则 |
|---|---|

| 识别结果 | UI 状态 |

## 2\.2 返佣关系树

**入口**：合伙人列表【返佣树】、详情或团队穿透页【返佣树 / 修改比例】。

**返回**：页头【← 返回】回到 **当前焦点合伙人的详情页**（`§2.1.4`），**不是**合伙人列表。若自穿透页进入返佣树，返回后亦进入该合伙人详情（不保留穿透栈层级）。

**核心原则**：无论从哪一层合伙人进入，树始终**锚定在该用户所属的一级合伙人根节点（L1 伞）**上展示完整业务线；进入深层的合伙人时，自动**定位并高亮**该节点，而非只展示以该节点为根的子树片段。

页面截图：[**后台 · 返佣关系树**](https://raw.githubusercontent.com/DashuaibiZZY/prototype/doc-assets/document/assets/%E5%90%88%E4%BC%99%E4%BA%BA/admin-rebate-tree.png)

### 2\.2\.1 页面结构

- **标题**：展示焦点合伙人备注 + 所属 L1 备注 +「返佣树」。

- **待提交修改条**：暂存未提交的比例变更，标注「权限内 · 即刻生效」或「超权限 · 提交审批」。

- **操作说明**：上级链固定展示；下级默认只展示直属合伙人，点 **+** 逐层展开；多条修改后统一【提交修改】。

- **定位搜索**：在当前 L1 伞内按钱包 / UID 搜索；自动展开路径、翻页到正确的一级直属支路页、高亮节点并滚动到视区。**不会**因定位而折叠整树为单一路径。

### 2\.2\.2 树形展示规则

**一级入口节点**：L1 根固定在顶部；当焦点为 L1 时标记「当前」。

**上级链**：自焦点向上追溯至 L1，完整展示（无旁支）；链上节点均可编辑比例。

**向下展开**：

- **一级直属支路分页**：L1 的**直接下级**合伙人按支路分页展示（10 条/页），每支路可 **+ / −** 展开更深层级。

- 每个节点展示：层级、钱包、UID、备注、可编辑的返佣比例输入框。

**级差规则**：下级返佣比例**不得大于**直属上级（允许相等，级差为 0）。在输入框暂存变更时，若对含下级的节点**下调**比例，弹出提示列出直属下级当前比例，提醒确认级差影响。

### 2\.2\.3 比例修改与提交

运营在树上修改一个或多个节点比例后，变更进入「待提交修改」列表：

| 变更类型 | 新比例 vs 运营上限 | 提交后行为 |
|---|---|---|
| 权限内 | ≤ 运营上限且**非跨 BD** | 确认后**即刻生效** |
| 超权限 | &gt; 运营上限 | 每项生成一条「返佣比例调整（超出上限）」审批单；**审批通过后即刻生效** |
| 跨权限配置 | 调整对象归属**其他 BD 伞**（任意层级） | 须填**跨权限配置商务原因**；每项生成「返佣比例调整（跨权限配置）」审批单 → **风控 + 老板**；审批详情展示**原归属 BD** |

**确认提交弹窗**（点击【提交修改】后）：

页面截图：[**后台 · 返佣比例修改确认弹窗**](https://raw.githubusercontent.com/DashuaibiZZY/prototype/doc-assets/document/assets/%E5%90%88%E4%BC%99%E4%BA%BA/admin-modal-tree-confirm.png)

| 元素 | 规则 |
|---|---|
| 变更清单 | 每条展示钱包、原比例 → 新比例、生效方式标签 |
| 混合批提示 | 若同时存在权限内与超权限项：提示仅超权限项进审批，权限内项将**自动放弃**并回滚输入框 |
| 修改原因备注 | **必填** |
| 跨权限配置商务原因 | 含跨 BD 项时展示并**必填** |
| 图片附件 | 最多 **4 张**图片（PNG 等）；超上限审批时随审批单保存，供风控/老板查看 |

**确认逻辑**：

- 全部为权限内：确认后批量**即刻生效**；若含下调且该节点有下级，须二次确认级差风险。

- 全部为超权限：仅提交审批，不立即改比例；**审批通过后即刻生效**。

- 混合：用户确认后，超权限项提交审批；权限内项放弃并回滚；超权限项**审批通过后即刻生效**。

- 超权限审批通过后，由后台执行比例更新（与一级绑定超上限审批同理，**即刻生效**）。

## 2\.4 合伙人审核

**访问路径**：侧栏 → 「合伙人审核」（页内标题可为「合伙人配置审批」）

**页面作用**：处理三类合伙人配置变更审批；风控、老板切换角色 Tab 处理待办。

### 2\.4\.1 审批类型与流程

| 审批类型 | 触发场景 | 审批流 | 生效时机 |
|---|---|---|---|
| 一级合伙人绑定（超上限） | 新增一级合伙人且比例 &gt; 运营上限 | 市场运营提交 → **风控** → **老板**（风控通过后同步 Lark） | **审批通过后即刻生效** |
| 返佣比例调整（超出上限） | 返佣树提交且单项新比例 &gt; 运营上限 | 同上 | **审批通过后即刻生效** |
| 返佣关系迁移 | 迁移返佣关系页提交 | 市场运营提交 → **风控** → 通过即生效 | **审批通过后即刻生效** |
| 一级合伙人绑定（跨权限） | 绑定对象为其他 BD 伞下合伙人 | 市场运营提交 → **风控** → **老板** | **审批通过后即刻生效** |
| 返佣比例调整（跨权限配置） | 返佣树调整对象为其他 BD 伞下合伙人 | 同上 | **审批通过后即刻生效** |
| 返佣关系迁移（跨权限配置） | 迁移主体为其他 BD 伞下合伙人 | 同上 | **审批通过后即刻生效** |

**无需审批的配置**（≤ 运营上限且**非跨 BD** 的一级绑定、返佣树比例调整）提交后**即刻生效**。

**第一步：总量对账（宏观核减）** — 打开表 1，校验净手续费与「平台留存 + 返佣总预算」守恒；结合表 2a 按 L1 校验各业务线是否超「一级理论最大原始应发」。

**第二步：系统聚合校验** — 对表 3 做枢纽分析，按获得者地址汇总分账金额。

**第三步：差异比对** — 表 4 与第二步结果 VLOOKUP，差异列须全为 0。

**第四步：穿透抽样** — 抽检代理，核对表 3 分账比例与表 2 级差关系一致。

## 3\.4 佣金结算与发放

**访问路径**：侧栏 → 「佣金结算记录」

**页面标题**：佣金结算与发放

**页面作用**：展示佣金汇总与按日结算流水；让用户知晓每日交易额、返佣金额与结算状态。

页面截图：[**Web · 佣金结算与发放**](https://raw.githubusercontent.com/DashuaibiZZY/prototype/doc-assets/document/assets/%E5%90%88%E4%BC%99%E4%BA%BA/web-settlement.png)

### 3\.4\.1 汇总卡片（3 张）

| 卡片 | 说明 |
|---|---|
| 待结算佣金（今日预估） | 当前自然日预估、尚未进入最终放款的佣金 |
| 已结算总额（累计） | 历史已成功发放累计 |
| 昨日发放佣金 | 最近一个已完成发放日的实发金额及成功状态 |

### 3\.4\.2 每日结算流水

**筛选**：

- 结算日期（日期选择器，按日过滤）。

- 结算状态：全部 / 待结算 / 已结算（**不含**已移除的「返佣异常停止结算」等异常停结状态，见 §1.5）。

**表格列**：

| 列名 | 说明 |
|---|---|
| 结算日期 | 对应自然日（日结周期见 §1.3） |
| 交易额 | 当日参与返佣计算的有效成交额 |
| 返佣金额 | 当日应展示给用户的返佣金额（**已调减实发时展示调减后实发**）；若存在违规扣减，主行下方红色小字 **违规 −$XX**（= 后台批次明细调减差额） |
| 结算状态 | 见下表 |

**用户侧结算状态（每日流水）**：

| 展示状态 | 业务含义 |
|---|---|
| **待结算** | 该日佣金尚未完成放款，含：批次等待对账、后台批次**已拒绝**打回重算（用户侧统一显示待结算）、或后台在批次明细中**调减实发**后尚未放款（此时可展示违规扣减次行）；**或用户/合伙人处于冻结状态**导致暂停日结发放、累计待解冻后统一发放 |
| **已结算** | 该日佣金已审核通过并完成发放 |

分页：10 条/页。

### 3\.4\.3 与后台对账的对应关系（产品口径）

| 后台事实 | 用户流水展示 |
|---|---|
| 批次等待对账 | 待结算 |
| 批次已拒绝 | 待结算（不暴露拒绝） |
| 批次明细调减实发（尚未放款） | 待结算；返佣主行 = 调减后实发；次行 **违规 −$XX** = 调减差额 |
| 批次已放款 | 已结算 |
| 风控调减实发（已随批次放款） | 已结算；返佣主行 = 最终实发；次行 **违规 −$XX** = 调减差额 |

## 3\.5 合伙人层级限制（摘要）

与 §1.4 一致：

- 平台对合伙人账号设置**最多 10 层**合伙人层级（L1 为一级合伙人，向下至多 10 层合伙人节点）。

- 合伙人**新增下级合伙人**时，若会导致链路深度超过 10 层，系统**禁止绑定**新下级。该限制约束的是**新增发展**，不自动裁切已存在的深层节点。

- 直客绑定、交易、返佣计算不受「10 层」约束（直客不计入合伙人层数）。
