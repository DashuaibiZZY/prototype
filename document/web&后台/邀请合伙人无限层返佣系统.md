# 邀请合伙人无限层返佣系统

# 业务定义

## 1\.1 核心业务模型

**模型定义：无限级差佣金制**

- 平台为每个一级代理设定一个返佣比例上限（如 70%），该比例即为此代理整条业务线的“总佣金包”。

- 代理可以无限层级地发展下级代理，每一级代理的返佣比例由其直属上级设定，且必须小于或等于上级自身的比例。

- 当终端用户（直客或代理自营）产生交易手续费时，系统沿邀请链路向上逐级计算级差佣金，直到一级代理为止。

    

**角色定义**

|角色|账号类型|交易时身份|是否参与返佣分配|
|---|---|---|---|
|一级代理|Agent|渠道/交易者|是，享受自返佣，并从下级代理的级差中获利|
|N级代理 \(N≥2\)|Agent|渠道/交易者|是，享受自返佣，并从直属下级代理的级差中获利|
|直客|Client|纯交易者|是，为上级代理贡献级差的“燃料”，自己不拿返佣|

**核心原则：代理自营也参与返佣**

- 代理用自己的代理账号交易，自己拿走自己返佣比例对应的佣金（自返佣）。

- 同时，他的所有上级依然按级差规则分钱。



## 1\.2 返佣计算规则

### 规则一：自返佣

- 触发条件：代理使用自己的代理账号进行交易并产生手续费。

- 计算：`该代理的返佣比例 × 该笔手续费`

- 拿到钱的人：该代理本人。

    

### 规则二：直客级差

- 触发条件：直客进行交易并产生手续费。

- 计算：

    - 直客的直属上级代理：拿走自己**全额**返佣比例对应的佣金。

    - 该上级的每一位上级：拿走 `(自己的返佣比例 - 直属下级代理的返佣比例)` 的级差部分。

- 如果上级与直属下级的比例相同，则该上级在这笔直客交易上级差为 0。

    

### 规则三：代理自营级差

- 触发条件：某代理用自己代理号交易产生手续费。

- 该代理自己先拿走自返佣（规则一）。

- 他的所有上级，按规则二的方式，从他身上计算级差，即 `(上级比例 - 该代理比例) × 该笔手续费`。

    

### **公式总结：**

- 对任意一笔交易：

    1. 确定交易发起人 `X`（可能是代理或直客）。

    2. 如果 `X` 是代理，`X` 获得 `比例_X × 手续费`。

    3. 沿着 `X` 的上级链路向上遍历，当前上级 `P`：

        - 如果 `P` 是 `X` 的直属上级，`P` 获得 `(比例_P - 比例_X) × 手续费`

        - 否则，`P` 获得 `(比例_P - 比例_直属下级) × 手续费`

    4. 直到一级代理停止。

        

## 1\.3 返佣结算流程

**整体流程：日结制**

1. **交易数据采集**：系统实时记录每一笔交易的手续费。

2. **每日结算触发**：每日 00:00 \(UTC\+8\)，系统对前一日 00:00:00 至 23:59:59 的所有交易进行结算。

3. **数据同步**：生成用于审查的四个 CSV 文件，进入风控审批队列。

4. **人工审查**：风控或运营人员登录后台“佣金对账与发放”页面，进行四步审计：

    - **总量对账**：用 Platform\_Summary 核对平台总手续费与总返佣预算。

    - **聚合校验**：用 Rebate\_Split\_Detail 的流水表通过 Excel 枢纽分析，反向汇总每个代理应得总金额。

    - **差异比对**：将汇总结果与 System\_Proposed\_Payout 做 VLOOKUP 比对，排查是否存在非零差异。

    - **穿透抽样**：随机抽检一个代理，验证其分账流水是否与 Affiliate\_Map 中的比例关系吻合。

5. **审批执行**：

    - **通过**：风控点击“审核通过并放款”，系统将最终实发金额执行发放。

    - **拒绝**：风控填写拒绝原因，该批次标记为“已拒绝”，打回重算。

6. **数据归档**：所有 CSV 文件和审批记录存档备查。



## 1\.4 返佣比例调整与异常配置保护

- **比例调整触发检查**：当任何代理的返佣比例被调低时（无论是平台调一级，还是上级调下级），系统必须实时检查该代理名下**所有直属下级**的返佣比例。

- **异常判定标准**：若存在  `下级返佣比例 > 该代理新返佣比例` ，则判定为**配置异常**。

- **异常影响范围**：以该代理为起点的**整条下游佣金链**（包含该代理自身、他所有下级、下下级…），从**发生异常的当下起**，立即停止参与每日返佣结算计算。

- **异常状态标记**：该链路上的所有代理，其“结算状态”被系统标记为  `待修正返佣后计算` 。在此期间他们产生的交易手续费仍正常记录，但不产生任何级差佣金分录，也不会计入任何人的“待结算佣金”。

- **修正与恢复**：

    - 代理需要自己进入“代理管理页”，找到比例高于自己的下级，**手动将其比例调低至合规**。

    - 一旦该代理名下所有直属下级比例均 ≤ 自身比例，系统自动解除异常标记，**立即恢复**结算资格。

    - 恢复后，下一个结算周期（每日00:00）将对**该链路从异常开始到恢复正常期间所有未结算的交易**，用**修正后的新比例**重新计算佣金，并合并到当日批次中发放。



## 1\.5 其他补充

### **活跃用户 / 活跃代理定义**

- 定义为“所选时间周期内，交易额 \> 0 的用户或代理”。

- 此指标为**查询时实时计算**，不需要数据落库，不需要维护每日活跃状态表。

- 举例：选择时间筛选为“过去7天”，则统计近7天内有过至少一笔交易（交易额 \> 0）的用户/代理数量。

### 2\.1\.3 调整返佣比例流程

1. 点击代理列表行的【调整】按钮，弹出  `modal-modify-ratio`  弹窗。

    - 弹窗内容：正在操作的代理地址/备注、当前配置比例（动态显示）、新比例输入框。

    - 提示：“修改将于次日 00:00 生效。”

2. 输入新比例后点击【确认修改】，系统判断：

    - 若新比例**大于等于**当前比例（上浮），直接保存，提示成功，不触发异常检查。

    - 若新比例**小于**当前比例（下调），且**大于等于**所有直属下级的最高比例，直接保存，提示成功。

    - 若新比例**小于**当前最高下级比例（存在产生倒挂风险），则**关闭输入弹窗**，自动弹出  `modal-confirm-adjust`  风险确认弹窗。

3. 风险确认弹窗内容：

    - 橙色警告图标 \+ “确认修改返佣比例？”

    - 提示文案：“下调一级代理的比例可能导致其与直属下级代理之间产生比例倒挂。”

    - 显示“当前比例”和“目标比例”（动态填入）。

    - 点击【确认并变更】后，提交修改，系统执行异常检查，标记异常代理，暂停相关链路结算。提示“比例调整指令已提交，T\+1 生效”。

    - 点击【取消】放弃修改。

    

**业务规则**：

- 运营可以上调或下调一级代理的返佣比例。

- 上调不触发异常检查，直接生效。

- 下调时，不硬性阻止操作，但若可能产生倒挂，需二次确认，确认后系统自动执行异常检测和链路保护。

- 比例调整即时生效用于异常检测，佣金计算从次日 00:00 起使用新比例。

#### **风控实操案例 \(审计流程\)：**

风控拿到导出的四个 CSV 文件后，无需一个个查代理，而是通过以下四个步骤进行全量校验：



**第一步：总量对账（宏观核减）**

- **操作**：打开 `表1 (Platform_Summary)`。

- **检查点**：

    1. 校验 `全站净手续费` 是否等于数据库导出的当日总手续费（剔除做市商）。

    2. 校验 `平台留存收入 + 全站返佣总预算` 是否等于 `全站净手续费`。

- **目的**：确保系统没有在初始计算时“算凭空了”或者“漏算了”总钱数。



**第二步：系统聚合校验（自动化重算）**

- **操作**：

    1. 打开 `表3 (Rebate_Split_Detail)`。

    2. 插入**枢纽分析表（Pivot Table）**。

    3. 设置：“佣金获得者地址”**作为“行”，**“最终分账金额”作为“值（求和）”。

    4. 将该枢纽表的结果复制到新表，命名为“风控手算汇总”。

- **目的**：利用 Excel 的聚合能力，从最底层的流水反向推导出每个代理“应得的总钱数”。



**第三步：差异比对（核心审计）**

- **操作**：

    1. 打开 `表4 (System_Proposed_Payout)`。

    2. 在 `表4` 后面增加一列“风控校验值”，通过 `VLOOKUP` 函数从第二步产生的“风控手算汇总”中抓取对应地址的金额。

    3. 增加一列“差异值”，公式：`系统待结算返佣总额 - 风控校验值`。

- **检查点**：全选“差异值”列，检查是否有非 0 的数字。

- **目的**：**这是最关键的一步。** 如果有差异，说明 `表4`（后台显示的钱）和 `表3`（实际流水记录）不一致，系统存在逻辑 Bug，立即拒绝该批次。



**第四步：穿透抽样（逻辑验证）**

- **操作**：

    1. 从 `表4` 中挑一个二级或三级代理。

    2. 去 `表3` 中过滤这个代理作为“获得者”的所有记录。

    3. 随机选一行“源交易用户地址”，拿到该用户的 `Net Fee`。

    4. 去 `表2 (Affiliate_Map)` 搜这个“源用户”和“获得者”，看他们的比例差是否等于 `表3` 记录的 `分账级差比例`。

- **目的**：验证系统在处理无限层级差时的“加减法”逻辑是否按预设规则运
